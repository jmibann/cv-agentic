# Internationalization (en / es)

## Decisions

- Languages: **`en`** and **`es`**. Default if it cannot be resolved: **`en`**.
- Visible selector: `LanguageSwitcher` (EN | ES) in the ControlsBar, next to the `ThemeToggle`.
- **No i18n library**: a typed `LocaleProvider` of our own. With 2 languages and
  ~25 interface texts, `react-i18next` or similar are not justified.

## Resolving the initial language

1. Stored preference: `localStorage["cv:locale"]` (`"en"` | `"es"`).
2. Browser language: first value of `navigator.languages`; if it starts with
   `es` → `es`, otherwise → `en`.
3. Default: `en`.

It is resolved by the **anti-flash script** in `index.html` (see `theming.md`), which leaves it
in `<html lang>`. The `LocaleProvider` takes its initial state from there.

## Where each text lives

| Kind | File (in the app) | TS type |
|---|---|---|
| CV content | `src/content/cv.en.json`, `src/content/cv.es.json` | `CvData` from `@data/cv.types.generated` |
| Interface texts | `src/i18n/ui.en.ts`, `src/i18n/ui.es.ts` | `UiStrings` (derived from `ui.en.ts`) |

### Content: one JSON per language, validated with JSON Schema

The CV content lives in **JSON** so it can be edited without touching code.

- **Source of truth for the format:** `data/cv.schema.json` (JSON Schema
  draft-07). The TS types are **generated** from it into
  `data/cv.types.generated.ts` (`gen:types` script, with
  `json-schema-to-typescript`); that file is not edited by hand.
- **Editing:** each JSON declares `"$schema"` pointing to the schema, so the
  editor (VS Code) autocompletes fields, shows each one's `description`
  and flags errors while typing:

  ```json
  {
    "$schema": "../../data/cv.schema.json",
    "locale": "en",
    "profile": { "name": "…", "headline": "…", "avatar": { "src": "/images/avatar.webp" }, "about": ["…"] },
    "contact": [], "social": [], "services": [], "education": [],
    "experience": [], "projects": [], "skills": [], "testimonials": []
  }
  ```

- **Validation:** when importing a `.json`, TypeScript loses the literals
  (`"github"` becomes `string`), so the type is not enough: it is validated with
  **ajv**. The `build:validator` script compiles the schema into a
  precompiled function (`data/validate-cv.generated.js`, ajv's *standalone* mode,
  without loading ajv in the browser) that works as a *type guard*:

  ```ts
  // src/content/index.ts
  import type { CvData, Locale } from "@data/cv.types.generated";
  import { validateCv } from "@data/validate-cv.generated";
  import en from "./cv.en.json";
  import es from "./cv.es.json";

  function load(raw: unknown, file: string): CvData {
    if (!validateCv(raw)) {
      throw new Error(`Invalid content in ${file}: ${JSON.stringify(validateCv.errors)}`);
    }
    return raw;
  }

  export const cvByLocale: Record<Locale, CvData> = {
    en: load(en, "cv.en.json"),
    es: load(es, "cv.es.json"),
  };
  ```

- **An invalid JSON breaks the build and the tests:** `validate:content` runs
  before `build` (`prebuild`) and `content.test.ts` imports the content.
- **Non-translatable fields — canonical list** (they must be identical in
  `cv.en.json` and `cv.es.json`; `content.test.ts` compares exactly these):

  | Path | Why |
  |---|---|
  | every `id` | stable identity of each entry |
  | `profile.avatar.src`, `profile.downloadCvUrl` | file paths |
  | `contact[].type`, `contact[].href` | type and target of the link |
  | `social[].network`, `social[].url` | brand and profile URL |
  | `services[].icon` | icon from a closed list |
  | `education[].start/end`, `experience[].start/end`, `projects[].start/end` | dates |
  | `testimonials[].avatar.src` | file path |

  Everything else is translatable and **may** differ, even if in practice
  it matches: `profile.name`, `contact[].value` (e.g. a location written
  differently), `testimonials[].author`. In the schema, these fields carry
  "Not translatable" in their `description` (same list).
- **Bundle:** `content/index.ts` imports both languages statically, so
  both JSON files ship in the bundle. It is acceptable with 2 languages and a few KB;
  if languages are added or the content grows, move to a dynamic `import()` per
  language (noted in `docs/BACKLOG.md`).
- Full examples: `data/cv.example.en.json` and `data/cv.example.es.json`.
- Closed lists (`locale`, `type`, `network`, `icon`): the schema's `enum`;
  their values for iterating in code are in `@data/constants`.

## `LocaleProvider`

```ts
type Locale = "en" | "es";

interface LocaleContextValue {
  locale: Locale;
  setLocale: (locale: Locale) => void; // sets <html lang>, stores it
  t: UiStrings;                        // interface texts of the active language
}
```

Hooks:

- `useLocale()` → `LocaleContextValue` (error if there is no provider).
- `useCv()` → `CvData` of the active language. **Components never pick the
  language or import the content**: they receive data through props from the pages,
  and the pages get it with `useCv()`.

## Dates and periods

- In the data: `start` / `end` as `"YYYY"` or `"YYYY-MM"`; `end: null` = current.
- Pure function `formatPeriod({ start, end }, locale, presentLabel)` in
  **`src/i18n/formatPeriod.ts`** (foundation creates it in F1, with its tests,
  because Timeline needs it in F3):
  - `"2015"`, `null` → `"2015 — Present"` / `"2015 — Actualidad"`
  - `"2019-03"`, `"2021-11"` → `Intl.DateTimeFormat(locale, { month: "short", year: "numeric" })`
    on each end → `"Mar 2019 — Nov 2021"` / `"mar 2019 — nov 2021"`.
  - Separator: `" — "` (em dash with spaces).
- It is rendered with `<time dateTime="2019-03">` on each end. For that,
  **`formatPeriodEndpoint(value, locale)`** exports the per-end formatting
  (F3 Change, decision 12=a: Timeline renders one `<time>` per date with its formatted
  text; `formatPeriod` keeps its signature and behavior, and its
  private `formatEndpoint` becomes this exported function).

## Expected tests

- **Content parity** (`content.test.ts`): `cv.en.json` and `cv.es.json`
  have the same ids in each collection, in the same order, and the
  non-translatable fields are identical.
- **Date order** (`content.test.ts`): in each entry of `education`,
  `experience` and `projects` in both languages, `start` ≤ `end` when `end` is not `null`
  (normalizing `"YYYY"` as `"YYYY-01"` in `start` and as `"YYYY-12"` in
  `end`, so that `start "2017-06"` with `end "2017"` is valid; with both in
  `"YYYY-MM"` format the string comparison is already chronological).
  Test cases: `2017-06`→`2017` valid; `2018`→`2017` invalid;
  `2017-06`→`2017-05` invalid. The valid format is guaranteed by the `pattern`
  of `YearMonth` in the schema (validated by ajv).
- **Invalid content** (`content.test.ts`): the validator rejects a month
  `99`, an unknown network and an extra field (in-memory test cases).
- `LocaleProvider`: takes the initial language from `<html lang>`; `setLocale` changes
  `lang`, persists and changes `t`; storage that throws does not break it.
- `useCv()` returns the content of the active language.
- `formatPeriod`: years, year-month, `end: null`, both languages.
- `formatPeriodEndpoint`: same cases per end (a bare year as is; `"YYYY-MM"` → short month + year in en/es).
- `format`: replacement of one or several `{placeholders}`, a missing placeholder stays literal.

## What is NOT translated through the URL

The language does not go in the URL (there is no `/es/…`). The hash (`#about`, `#resume`) is
the same in both languages. Reason: a single-page site, with no per-language SEO
in this scope (noted in `docs/BACKLOG.md`).
