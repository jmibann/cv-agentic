# Internacionalización (en / es)

## Decisiones

- Idiomas: **`en`** y **`es`**. Default si no se puede resolver: **`en`**.
- Selector visible: `LanguageSwitcher` (EN | ES) en la ControlsBar, junto al `ThemeToggle`.
- **Sin librería de i18n**: un `LocaleProvider` propio y tipado. Con 2 idiomas y
  ~25 textos de interfaz, `react-i18next` o similares no se justifican.

## Resolución del idioma inicial

1. Preferencia guardada: `localStorage["cv:locale"]` (`"en"` | `"es"`).
2. Idioma del navegador: primer valor de `navigator.languages`; si empieza con
   `es` → `es`, si no → `en`.
3. Default: `en`.

Lo resuelve el **script anti-flash** de `index.html` (ver `theming.md`) y lo deja
en `<html lang>`. El `LocaleProvider` toma su estado inicial de ahí.

## Dónde vive cada texto

| Tipo | Archivo (en la app) | Tipo TS |
|---|---|---|
| Contenido del CV | `src/content/cv.en.json`, `src/content/cv.es.json` | `CvData` de `@data/cv.types.generated` |
| Textos de interfaz | `src/i18n/ui.en.ts`, `src/i18n/ui.es.ts` | `UiStrings` (derivado de `ui.en.ts`) |

### Contenido: un JSON por idioma, validado con JSON Schema

El contenido del CV vive en **JSON** para que se edite sin tocar código.

- **Fuente de verdad del formato:** `data/cv.schema.json` (JSON Schema
  draft-07). Los tipos TS se **generan** desde ahí en
  `data/cv.types.generated.ts` (script `gen:types`, con
  `json-schema-to-typescript`); ese archivo no se edita a mano.
- **Edición:** cada JSON declara `"$schema"` apuntando al esquema, así el
  editor (VS Code) autocompleta campos, muestra la `description` de cada uno
  y marca errores mientras se escribe:

  ```json
  {
    "$schema": "../../data/cv.schema.json",
    "locale": "en",
    "profile": { "name": "…", "headline": "…", "avatar": { "src": "/images/avatar.svg" }, "about": ["…"] },
    "contact": [], "social": [], "services": [], "education": [],
    "experience": [], "skills": [], "testimonials": []
  }
  ```

- **Validación:** al importar un `.json`, TypeScript pierde los literales
  (`"github"` pasa a `string`), así que el tipo no alcanza: se valida con
  **ajv**. El script `build:validator` compila el esquema a una función
  precompilada (`data/validate-cv.generated.js`, modo *standalone* de ajv,
  sin cargar ajv en el navegador) que funciona como *type guard*:

  ```ts
  // src/content/index.ts
  import type { CvData, Locale } from "@data/cv.types.generated";
  import { validateCv } from "@data/validate-cv.generated";
  import en from "./cv.en.json";
  import es from "./cv.es.json";

  function load(raw: unknown, file: string): CvData {
    if (!validateCv(raw)) {
      throw new Error(`Contenido inválido en ${file}: ${JSON.stringify(validateCv.errors)}`);
    }
    return raw;
  }

  export const cvByLocale: Record<Locale, CvData> = {
    en: load(en, "cv.en.json"),
    es: load(es, "cv.es.json"),
  };
  ```

- **Un JSON inválido rompe el build y los tests:** `validate:content` corre
  antes de `build` (`prebuild`) y `content.test.ts` importa el contenido.
- **Campos no traducibles — lista canónica** (deben ser idénticos en
  `cv.en.json` y `cv.es.json`; `content.test.ts` compara exactamente estos):

  | Ruta | Por qué |
  |---|---|
  | todos los `id` | identidad estable de cada entrada |
  | `profile.avatar.src`, `profile.downloadCvUrl` | rutas de archivos |
  | `contact[].type`, `contact[].href` | tipo y destino del link |
  | `social[].network`, `social[].url` | marca y URL del perfil |
  | `services[].icon` | ícono de una lista cerrada |
  | `education[].start/end`, `experience[].start/end` | fechas |
  | `testimonials[].avatar.src` | ruta de archivo |

  Todo lo demás es traducible y **puede** diferir, aunque en la práctica
  coincida: `profile.name`, `contact[].value` (p. ej. una ubicación escrita
  distinta), `testimonials[].author`. En el esquema, estos campos llevan
  "No traducible" en su `description` (misma lista).
- **Bundle:** `content/index.ts` importa ambos idiomas de forma estática, así
  que los dos JSON van en el bundle. Es aceptable con 2 idiomas y pocos KB;
  si se agregan idiomas o el contenido crece, pasar a `import()` dinámico por
  idioma (anotado en `docs/BACKLOG.md`).
- Ejemplos completos: `data/cv.example.en.json` y `data/cv.example.es.json`.
- Listas cerradas (`locale`, `type`, `network`, `icon`): `enum` del esquema;
  sus valores para recorrer en código están en `@data/constants`.

## `LocaleProvider`

```ts
type Locale = "en" | "es";

interface LocaleContextValue {
  locale: Locale;
  setLocale: (locale: Locale) => void; // fija <html lang>, guarda en storage
  t: UiStrings;                        // textos de interfaz del idioma activo
}
```

Hooks:

- `useLocale()` → `LocaleContextValue` (error si no hay provider).
- `useCv()` → `CvData` del idioma activo. **Los componentes nunca eligen el
  idioma ni importan el contenido**: reciben datos por props desde las páginas,
  y las páginas los obtienen con `useCv()`.

## Fechas y períodos

- En los datos: `start` / `end` como `"YYYY"` o `"YYYY-MM"`; `end: null` = actual.
- Función pura `formatPeriod({ start, end }, locale, presentLabel)` en
  **`src/i18n/formatPeriod.ts`** (la crea foundation en F1, con sus tests,
  porque Timeline la necesita en F3):
  - `"2015"`, `null` → `"2015 — Present"` / `"2015 — Actualidad"`
  - `"2019-03"`, `"2021-11"` → `Intl.DateTimeFormat(locale, { month: "short", year: "numeric" })`
    en cada extremo → `"Mar 2019 — Nov 2021"` / `"mar 2019 — nov 2021"`.
  - Separador: `" — "` (raya con espacios).
- Se renderiza con `<time dateTime="2019-03">` en cada extremo. Para ello,
  **`formatPeriodEndpoint(value, locale)`** exporta el formateo por extremo
  (Cambio F3, decisión 12=a: Timeline pinta un `<time>` por fecha con su texto
  formateado; `formatPeriod` mantiene firma y comportamiento, y su
  `formatEndpoint` privada pasa a ser esta función exportada).

## Tests esperados

- **Paridad de contenido** (`content.test.ts`): `cv.en.json` y `cv.es.json`
  tienen los mismos ids en cada colección, en el mismo orden, y los campos no
  traducibles son idénticos.
- **Orden de fechas** (`content.test.ts`): en cada entrada de `education` y
  `experience` de ambos idiomas, `start` ≤ `end` cuando `end` no es `null`
  (normalizando `"YYYY"` como `"YYYY-01"` en `start` y como `"YYYY-12"` en
  `end`, para que `start "2017-06"` con `end "2017"` sea válido; con ambos en
  formato `"YYYY-MM"` la comparación de strings ya es cronológica).
  Casos de test: `2017-06`→`2017` válido; `2018`→`2017` inválido;
  `2017-06`→`2017-05` inválido. El formato válido lo garantiza el `pattern`
  de `YearMonth` en el esquema (validado por ajv).
- **Contenido inválido** (`content.test.ts`): el validador rechaza un mes
  `99`, una red desconocida y un campo extra (casos de prueba en memoria).
- `LocaleProvider`: toma el idioma inicial de `<html lang>`; `setLocale` cambia
  `lang`, persiste y cambia `t`; storage que lanza no rompe.
- `useCv()` devuelve el contenido del idioma activo.
- `formatPeriod`: años, año-mes, `end: null`, ambos idiomas.
- `formatPeriodEndpoint`: mismos casos por extremo (año suelto tal cual; `"YYYY-MM"` → mes abreviado + año en en/es).
- `format`: reemplazo de uno o varios `{placeholders}`, placeholder ausente queda literal.

## Qué NO se traduce por URL

El idioma no va en la URL (no hay `/es/…`). El hash (`#about`, `#resume`) es
el mismo en ambos idiomas. Motivo: sitio de una sola página, sin SEO por idioma
en este alcance (queda anotado en `docs/BACKLOG.md`).
